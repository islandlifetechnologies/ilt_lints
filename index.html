Linter rules

Custom lint rules for use in ILT projects. Includes rules for code style, testability, performance, and quality-of-life utility that can turn required boilerplate code into a simple quick fix.

With the exception of the export_library lint, the lints are all enabled by default when the ilt_lints package is included in your project's analysis_options.yaml as follows:

YAML 
include: package:ilt_lints/lints.yaml
14 Total Rules 13 with Quick Fix

Overview

Each linter rule below documents what the rule checks, why it matters, BAD and GOOD Dart code examples, and how to enable or configure the rule in analysis_options.yaml.

Quick fixes: Rules marked with the quick fix badge include an automated fix that can be applied directly in your IDE or via the CLI.

Enabling rules

To enable custom lint rules in your project, configure the plugin diagnostics in your analysis_options.yaml file:

analysis_options.yaml 
plugins:
  ilt_lints:
    version: ^2.0.0
    diagnostics:
      avoid_large_ccn: true
      export_library: true
      prefer_const_constructors: true
      prefer_named_parameters: true
      prefer_primary_constructors: true
      sort_fields: true
      sort_functions_alphabetically: true
      sort_functions_by_scope: true
      sort_named_parameters: true
      sort_widget_functions: true
      sort_widget_parameters: true
      use_clock: true
      use_file_system: true
      valid_json_serializable: true

avoid_large_ccn
View details →

AVOID deeply nested control flow and excessive branching in a single function; extract smaller, single-purpose helper functions or use early returns and polymorphism to keep cyclomatic complexity low.

Calculates the cyclomatic complexity number (CCN) for every function, method, and constructor and triggers when the complexity exceeds the configured ccn threshold (defaults to 20). Each conditional branch, loop, case, catch, ternary operator (?:), null-coalescing operator (??, ??=), and logical operator (&&, ||) increases the function's cyclomatic complexity.

export_library
Fix available View details →

DO Export all library source files from your package's exporter library file.

Ensures all files matching any include glob (and not matching any optional exclude glob) for a configured exporter file are exported by that exporter. If a file overlaps include and exclude, exclude wins.

prefer_const_constructors
Fix available View details →

DO Mark class constructors as const whenever the class can be constant without other changes.

Detects classes whose constructor (primary constructor or generative constructor) can be marked const without any other changes and flags them if not already marked const.

prefer_named_parameters
Fix available View details →

DO Use named parameters when a function has more than the configured number of positional parameters.

Triggers when a function, method, or constructor declares more than count positional parameters (defaults to 2). Supports configuring count in analysis_options.yaml.

prefer_primary_constructors
Fix available View details →

DO Use Dart primary constructors for classes instead of declaring constructors in the class body.

Detects classes that do not use a Dart primary constructor (class Foo(...) or class const Foo(...)) when a primary constructor can be used.

sort_fields
Fix available View details →

DO Sort fields above methods by scope, finality, and alphabetically within each group.

Ensures fields within a type body (classes, mixins, enums, extensions, and extension types) appear before all methods, getters, setters, and operators (ignoring constructors), grouped by scope (public static const, private static const, public static, private static, public instance, private instance), with final fields before non-final fields when final_first is enabled, and sorted alphabetically within each group.

sort_functions_alphabetically
Fix available View details →

DO Sort functions, getters, and setters alphabetically within each scope.

Ensures functions, getters, and setters within a type body (classes, mixins, enums, extensions, and extension types) are sorted alphabetically (lexicographically) within each scope. Fields, constructors, and operators are ignored. When sort_widget_functions is enabled, functions owned by sort_widget_functions in Widget and State classes are deferred to that rule.

sort_functions_by_scope
Fix available View details →

DO Sort functions, getters, and setters by static/instance and visibility scope.

Ensures functions, getters, and setters within a type body (classes, mixins, enums, extensions, and extension types) are sorted by scope: public static getters, public static setters, public static functions, private static getters, private static setters, private static functions, public getters, public setters, private getters, private setters, public instance functions, and private instance functions. Fields, constructors, and operators are ignored. When sort_widget_functions is enabled, functions owned by sort_widget_functions in Widget and State classes are deferred to that rule.

sort_named_parameters
Fix available View details →

DO Sort named parameters in declarations and named arguments at call sites alphabetically.

Ensures named parameters in function, method, and constructor declarations and named arguments at call sites are sorted alphabetically. Leading underscores on private named parameters are ignored when sorting so _foo sorts as foo. Supports required_first and ignore options in analysis_options.yaml.

sort_widget_functions
Fix available View details →

DO Sort widget lifecycle methods first (initState, didChangeDependencies, didUpdateWidget, deactivate, dispose), followed by other functions, then build* and _build* helper methods by scope, and build last.

Ensures functions within a Widget or State subclass are sorted in widget lifecycle and build order: initState, didChangeDependencies, didUpdateWidget, deactivate, dispose, other functions/getters/setters, public build* functions, private _build* functions, and finally build. Non-widget and non-state classes pass this rule automatically.

sort_widget_parameters
Fix available View details →

DO Place builder, child, children, and itemBuilder last, in alphabetical order.

Ensures the child, children, builder, and itemBuilder named parameters of a Widget constructor (and the matching named arguments of widget constructor invocations) come after all other named parameters, sorted alphabetically among themselves. Takes priority over sort_named_parameters for these parameters.

use_clock
Fix available View details →

DO Use clock.now() from package:clock/clock.dart instead of DateTime.now() in lib/ files.

Detects usages of DateTime.now() and DateTime.now tear-offs in files inside the lib/ folder (ignoring test/ and other non-lib/ directories) and requires using clock.now() / clock.now from package:clock/clock.dart so that time can be mocked in tests.

use_file_system
Fix available View details →

DO Use fs from package:io_ext/io_ext.dart and File, Directory, FileSystemEntity, and Link from package:file/file.dart instead of dart:io in lib/ files.

Detects direct usages of dart:io File, Directory, FileSystemEntity, and Link (including Directory.current and Directory.systemTemp) in files inside the lib/ folder (ignoring test/ and other non-lib/ directories) and requires using fs from package:io_ext/io_ext.dart (a FileSystem from package:file/file.dart) so file system operations can be overridden in tests with withFileSystem.

valid_json_serializable
Fix available View details →

DO Include the generated .g.dart part directive and define fromJson and toJson methods that call the generated json_serializable helpers.

Ensures classes annotated with @JsonSerializable include the generated part '<filename>.g.dart'; directive, define a valid fromJson factory or static method calling _$<ClassName>FromJson when createFactory is enabled, and define a valid toJson method calling _$<ClassName>ToJson when createToJson is enabled.
